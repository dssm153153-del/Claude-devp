# video-recreate-workflow

사용자가 참고 영상(바이럴 숏폼 등)을 주고 "이것과 같은 영상을 다른 캐릭터/장소로 만들자"고 할 때 사용한다. 대화는 한국어, 파일명은 영어.

역할 분담: 사용자는 GPT로 이미지를, Freepik(Wan, 시작·끝 이미지 방식)으로 영상을 직접 생성해 업로드한다. Claude는 분석, 설계, 프롬프트 작성, 결과 검수(ffmpeg/OpenCV), 프레임 추출, 최종 합본, 쓰레드 글 작성을 맡는다.

## 전체 순서 (건너뛰지 않는다)
1. 영상 분석
2. 씬 상세 설계 (스토리보드)
3. 샘플 이미지 (Ref-image)
4. 씬별 반복: GPT 이미지 생성 → Freepik 영상 생성 → 검수 → 컨펌 → 다음 씬
5. 최종 동영상 생성(합본)
6. 쓰레드 포스팅 샘플 글 작성

각 단계가 끝나면 사용자에게 컨펌을 받고 다음으로 넘어간다. 컨펌 없이 앞서가지 않는다.

## 핵심 규칙
1. 한 번에 하나씩. 한 턴에 아이템 1개(이미지 프롬프트 1개 또는 영상 프롬프트 1개)만 준다. 여러 개를 한꺼번에 주지 않는다.
1-1. 매 턴에는 지금 아이템에 필요한 정보만 준다(생성 초, 첨부, 설정, 프롬프트). 다음·전체 아이템 표나 미래 정보를 미리 주지 않는다. 설정이 바뀌면 그 아이템의 설정+프롬프트 전체를 다시 줘서 사용자가 위로 스크롤할 필요가 없게 한다.
2. 프롬프트는 항상 완전한 코드블록 1개. 공통 블록을 포함해 복사·붙여넣기만 하면 되게 한다. "이 문장을 추가하세요" 같은 조각 지시는 금지. 영상 프롬프트는 동작 설명 + 배경 고정 + `Avoid:` 목록을 한 블록에 넣는다.
3. 결과물을 받으면 직접 분석한다(프레임 추출, 컨택트시트, 프레임 차이). "좋아 보여요"가 아니라 통과/불합격과 근거(동작, 색, 연속성, 끝 튀는 프레임)를 말한다.
4. 실패하면 프레임으로 원인을 진단한 뒤 고친다. 프롬프트만 길게 늘리지 말고, 모델이 구조적으로 못 하는 동작인지도 판단한다.
5. 용어와 파일명을 혼용하지 않는다.
6. 요청 없이 커밋·푸시하지 않는다. 확정된 자산을 레포에 저장·커밋할지는 시작 때 한 번만 묻는다.
7. 매 턴 현재 위치를 "지금: C3-End 이미지 → 다음: K3 영상"처럼 이름으로 표시하고, 씬이 끝날 때마다 진행표(아이템 / 상태: 확정·진행·대기)를 보여준다.

## 매 턴 보내기 전 자가 점검 (어기면 사용자 한도 낭비)
보내기 전에 아래를 모두 확인하고, 하나라도 빠지면 고친 뒤 보낸다.
- [ ] 이미지 프롬프트: 첨부에 캐릭터 기준 Ref-image(해당 인물의 Ref-image-A/B)가 항상 들어 있는가. 직전 프레임(K{n-1}-Last)만 첨부하지 않는다. 형식: "생성 파일명: X / 첨부: 직전 프레임, Ref-image-?"(포스터·소품 기준 이미지가 따로 있으면 그것도).
- [ ] **첨부 파일 전송 규칙**: 사용자가 직접 만들어 올린 이미지·영상(GPT로 생성한 C 이미지, Freepik K 영상, Ref-image 등)은 사용자 PC에 이미 있으므로 **다시 보내지 않고 파일명만 정확히 표시**한다. 내가 만든 파일(영상에서 추출한 K{n}-Last, -aligned 보정본, 원본에서 뽑은 Pose-ref·Location-ref, 내가 편집한 이미지)만 같은 턴에 프롬프트보다 먼저 SendUserFile로 보내고 캡션에 파일명을 쓴다. 사용자가 받은 파일을 그 이름으로 저장하므로, 파일명을 바꾸거나 혼용하지 않는다.
- [ ] 첨부마다 무엇을 참조하고 무엇을 베끼지 말지(포즈·위치·소품) 프롬프트 첫 줄에 적었는가.
- [ ] 영상 프롬프트: 모델명, 시작·끝 이미지 파일명, 정확한 생성 초(N초)를 적었는가.
- [ ] 지금 아이템 하나만 주는가. 미래 아이템 표나 불필요한 설명을 빼고 짧게 쓴다.
- [ ] 검수는 프레임을 실제로 보고 수치(픽셀 차이·움직임)로 근거를 댔는가. 배속이 필요하면 원본과 나란히 비교한 미리보기를 보낸다.
- [ ] 앞 턴에서 사용자가 지적한 실수를 반복하지 않는가.

## 새 세션에서 이어서 작업할 때
- 먼저 `work/{project}/README.md`, `analysis/analysis.md`, `analysis/storyboard.md`, `scripts/build.py`를 읽어 컨셉·캐릭터·확정 자산·타이밍을 파악한다. 확정 이미지는 `images/`, 클립은 `clips/`, 추출 프레임은 `frames/`, 오디오는 `audio/`.
- 사용자는 Freepik(Wan 3.0, 초 단위 길이 지정)·GPT 이미지·Freepik 음악/효과음(ElevenLabs, 최소 3초)을 쓴다. 대화는 짧게, 한 아이템씩, "지금: X → 다음: Y" 표시.
- 사용자가 최종 편집을 직접 하는 경우가 있다. 편집본이 오면 그 영상을 기준으로 다시 분석한다.
- 사용자가 싫어한 것: 분석 대충하기, 컨펌 없이 다음 단계, 미래 아이템 표 나열, 첨부 누락, 이미 있는 파일 재전송, 같은 실패를 프롬프트만 바꿔 반복하기. 막히면 원인을 프레임·수치로 먼저 진단한다.

## 참고 프로젝트: 엘리베이터 낭떠러지 몰카 (work/video-recreate)
- 원본: 장난꾼이 엘리베이터 바닥에 낭떠러지 포스터를 깔고, 지인과 인사하느라 늦게 온 피해자가 바닥을 보고 안 타려고 문턱 앞에서 손잡이에 매달려 발버둥 → 일어나 황당 → 화나서 팔 뿌리치고 떠남.
- 고정 하이앵글 카메라(칸 안쪽 천장 모서리), 포스터는 평평한 인쇄물. 피해자 발은 끝까지 문턱 뒤.
- 결과: 클립 K1~K10b, 중간 키프레임(C6-Mid, C9-Mid, C10-Mid)로 동작 분할, 최종 `final/Final-audio.mp4`.

## 네이밍 규칙
- C = 이미지, K = 영상.
- `Ref-image.png`: 전체 기준 샘플 이미지(캐릭터·털색·표정·배경·조명). 여러 장이면 `Ref-image-A.png`, `Ref-image-B.png`.
- `C{n}-Start.png`: 씬 n의 시작 이미지. 첫 씬만 새로 생성하고, 이후는 직전 `K{n-1}-Last.png`를 그대로 쓰거나 필요한 부분만 편집한다.
- `C{n}-End.png`: 씬 n의 끝 이미지(새로 설계해 생성).
- `K{n}.mp4`: 씬 n의 영상. 재생성본은 `K{n}-v2.mp4`.
- `K{n}-Last.png`: K{n}에서 내가 뽑은 마지막 유효 프레임(끝 이미지로 튀는 프레임 직전).
- `C{n}-Mid.png`: 동작이 길거나 경계선을 넘을 위험이 있을 때 넣는 중간 키프레임(K{n}a/K{n}b로 분할).
- `C{n}-End-S1/S2.png`: 3단계 이미지 생성의 1·2단계 결과. `-aligned.png`: 직전 프레임 카메라에 맞춘 보정본.
- `Pose-ref-*.png`: 원본에서 뽑은 자세 참조 프레임. `A{n}-*.mp3`: 오디오 아이템.
- `Final-v{n}.mp4`: 합본 버전.
- `Threads-post.md`: 쓰레드 샘플 글.
- 폴더: `work/{project}/` 아래에 `analysis/`, `ref/`, `images/`, `clips/`, `frames/`, `final/`, `scripts/`, `copy/`.
- 사용자가 다른 이름으로 업로드해도 내가 위 이름으로 저장하고 알려 준다.
- 내가 지시한 생성 파일명이 곧 사용자 PC의 파일명이다. 사용자가 올린 파일에 내가 새 이름(-v1 등)을 붙여 첨부로 지시하지 않는다(사용자 PC에 없는 이름). 재생성은 첫 파일명을 그대로 두고 새 결과만 `-v2`, `-v3`로 이름 붙인다. 예: 첫 결과 `C1-Start.png`, 재생성 `C1-Start-v2.png`. 이미지를 보낼 때는 파일명을 캡션에 붙이고, 첨부해야 할 이미지를 이름으로 지시한다("첨부: Ref-image, K5-Last").

## 1단계: 영상 분석
분석이 틀리면 이후 모든 이미지·영상이 이상한 동작이 되어 "웃긴 영상"이 아니라 "비웃는 영상"이 된다. 작은 썸네일과 움직임 수치로 이야기를 짜 맞추지 않는다. 실제 실패 사례: 1fps/4fps 작은 컨택트시트만 보고 "문 밖에서 지인에게 작별 인사하다 늦게 엘리베이터를 타려는 사람"을 "엘리베이터 안에서 두리번거리는 사람"으로 오독했다.

1. 자동 측정: `python3 -I scripts/analyze.py <video> work/{project}/analysis/auto` (스킬 폴더의 `scripts/analyze.py`; 없으면 동일 로직으로 작성). opencv-python-headless가 없으면 먼저 설치한다. 결과:
   - `info.txt`: 해상도·fps·길이·오디오
   - `sheets/tXXX.png`: 2초마다 1장, 0.2초(5fps) 간격, 288px 폭, 프레임마다 타임코드 표시
   - `report.txt`: 컷 위치(프레임 차이 급증), 샷 목록, 0.5초 단위 움직임·줌 곡선, 반복 구간(티저·리플레이 자동 검출)
2. 시트를 처음부터 끝까지 한 장도 빼지 않고 직접 본다. 1fps 요약 시트만으로 결론 내지 않는다. 동작이 빠르거나 핵심인 구간은 10fps·더 큰 폭으로 다시 뽑아 본다.
3. 먼저 공간 구조를 확정한다: 카메라 위치(어디에 붙어 어느 쪽을 보는지), 화면의 위·아래·좌·우가 실제로 무엇인지(바닥/로비/문/손잡이), 인물이 어느 공간에 서 있는지, 화면 밖 인물·장소(지인, 입구 방향). 이걸 틀리면 동작 해석이 전부 틀린다.
4. 0.2초 단위 상세 타임라인 표를 쓴다: 시간 / 인물 / 시선 방향 / 팔·다리·몸 동작 / 소품 상태 / 문·배경 상태. "두리번거림"처럼 뭉뚱그린 단어 대신 "오른팔을 높이 들고 화면 왼쪽을 보며 손을 흔들고 게걸음"처럼 관찰한 그대로 쓴다.
5. 동기(왜 그 동작을 하는가)를 적는다: 예) 인사하느라 문 열린 걸 늦게 봄 → 바닥을 낭떠러지로 착각 → 타지 않으려고 손잡이에 매달려 다리를 차올림. 웃음 포인트는 동기와 반전에서 나온다.
6. 컷 표(번호, 시간, 내용, 티저·인서트 여부)와 페이스(정적·폭발 구간, 움직임 수치 근거)를 정리한다. 티저가 본편 어느 구간의 복사인지 수치로 밝힌다.
7. 웃음 포인트 목록을 만든다.
8. 시작 이미지 프롬프트를 쓰기 전에 그 구간의 핵심 소품·팔 동작을 0.3초 간격 고해상도 크롭으로 다시 확인한다. 실패 사례(threads-viral-01): 썸네일만 보고 "물병을 머리 위로 들어 붓기"로 오독 → 팔을 곧게 치켜든 시작 이미지 → 실제 원본은 굽힌 팔로 병을 얼굴 앞에 들었다가 자기 이마에 대고 옆으로 물을 뿜음. 시작 이미지 포즈는 원본 첫 프레임 포즈(팔꿈치 각도, 손 높이)와 다음 동작으로 이어지기 쉬운 자세여야 한다.
9. 결과를 `analysis/analysis.md`에 저장하고, 핵심 구간 시트를 SendUserFile로 같이 보여 주며 컨펌을 받는다. 사용자가 해석을 정정하면 그 구간을 다시 고해상도로 뽑아 확인한 뒤 고친다(사용자 말만 받아 적지 않는다).

## 2단계: 씬 상세 설계
분석 결과로 스토리보드 표를 만든다: 씬 번호, 상황, 카메라(시작/끝), 캐릭터별 동작과 포즈, 소품 상태, 표정·얼굴색 단계, 목표 길이, 속도 배수(합본 때 적용), 이음새 처리 메모, **생성 모델과 방식**.

### 씬별 모델·방식 선택 (내가 결정하고 이유와 함께 알린다)
사용자는 원하는 영상(참고 영상 + 바꿀 인물·장소)만 말한다. 나는 분석 결과로 씬마다 생성 방식과 모델을 정해 스토리보드 표에 적고, 컨펌 때 "씬 / 방식 / 모델 / 길이 / 예상 크레딧 / 선택 이유"를 한 표로 보여 준다. 기준(모델 표는 아래 "Freepik Kling 모델 목록"):
1. 원본에 재현할 동작이 있는 씬(사람·동물의 몸짓, 리액션, 발버둥, 춤 등) → **Kling 2.6 Motion Control**. 입력 = 시작 이미지(원본 구간 첫 프레임과 같은 구도·자세의 우리 인물, 3단계 방식) + 참조 영상(원본 구간, 내가 잘라 제공). 10초 초과 구간이거나 2.6 결과 품질이 부족하면 Kling 3.0 Motion Control.
2. 원본에 없는 동작·연결 클립(이음새 연결, 멈춤, 시작↔끝 사이 단순 이동) → **Kling 2.5(무제한)** Start/End. 품질 부족 시 Kling O1.
3. 인서트·정지 샷(풍경, 소품 클로즈업) → 이미지 1장 + 편집 줌/흔들림(생성 없음).
4. 입모양(대사)이 필요한 씬 → 2.6 Motion Control(Lip Sync).
5. **Motion Control은 1인 전용**으로 본다(Freepik 튜토리얼도 1인, threads-viral-01 K1: 3인 겹침+퇴장 참조 영상은 얼굴 모자이크·업스케일 후에도 생성 실패 반복). 한 컷에 2인 이상이 동시에 움직이면 스토리보드 단계에서 바로 Start/End(Kling 2.5 무제한 → 필요 시 O1)로 정한다. 실패를 보고서야 바꾸지 않는다.
- 첫 Motion Control 씬은 시험으로 보고 결과(동작 일치, 인물 유지, 배경 유지)를 검수한 뒤 나머지 씬의 방식을 확정한다. 결과·실패는 스킬에 기록한다.
- Motion Control 화면 사용법: 초(길이) 설정이 없다 — 결과 길이 = 참조 영상 길이. Start image와 Video(참조 영상)를 **둘 다** 올려야 Generate가 활성화된다. 그래서 참조 영상을 3~10초(3.0 MC는 3~15초)로 내가 잘라 `ref/Motion-K{n}.mp4`로 미리 보내고, 원본 구간이 3초보다 짧으면 느리게 늘려 3초 이상으로 만든 뒤 합본 때 다시 빠르게 한다.
- Motion Control 시작 이미지는 캐릭터마다 상반신(머리·양어깨·양팔·손·허리)이 화면 안에 다 있고, 다른 캐릭터·소품과 **겹치지 않게 사이를 띄운다**. 원본처럼 붙어 앉은 구도를 따라 그리면 Freepik이 "완전한 상반신이 감지되지 않음" 오류를 낸다(threads-viral-01 C1-Start, C1-Start-v3). 원본 거리보다 상반신 분리가 우선. 간격이 좋은 이미지가 나오면 새로 그리지 말고 그 이미지를 편집해 포즈만 고친다.
- Motion Control 생성이 계속 실패하면 비싼 모델로 바꾸기 전에 참조 영상을 의심한다: 실존 인물(정치인·연예인) 얼굴, 워터마크, 저해상도(528px 등). `scripts/blur_heads.py <in> <out>`(mediapipe 포즈+얼굴 검출, ±10프레임 합집합 모자이크, 2배 업스케일; 결과 .tmp.mp4를 ffmpeg libx264로 재인코딩)로 얼굴을 가린 `Motion-K{n}-v2.mp4`를 만들어 다시 시도한다. 필요: `pip install mediapipe opencv-python-headless`, `apt-get install libegl1 libgles2`, MP_MODELS 폴더에 모델 2개.
- Motion Control 프롬프트는 짧게: 한 줄 요약 + 인물 외형 + 유지 문단(같은 장소·조명, No new objects). 동작은 참조 영상이 담당하므로 동작 묘사는 최소화.
- 길이와 속도는 일부러 다양하게 설계한다(모두 5초·동일 속도 금지). 원본의 정적→빠른 접근→느린 클로즈업→빠른 퇴장 같은 리듬을 따른다.
- 얼굴색 변화처럼 모델이 클립 안에서 못 하는 것은 이 단계에서 이음새 편집으로 처리하기로 미리 정한다(아래 노하우 참고).
- 씬 목록 전체를 컨펌받고 시작한다. 이후 변경은 사용자와 합의 후 표를 갱신한다.

## 3단계: Ref-image
- 모든 것의 기준이 되는 샘플 이미지를 이미지 생성 전에 가장 먼저 만든다. 이 방식으로 품질이 확실히 좋아진다.
- Ref-image 프롬프트는 공통 블록을 담은 완전한 코드블록 1개.
- 공통 블록: 포토리얼리스틱 시네마틱, 9:16, 측면 눈높이, 85mm, 얕은 피사계심도, 골든아워 조명, 캐릭터 A/B 외형 묘사(털색·길이·표정), 두 발로 서기, 배경 설명, 소품 1개, "참조 이미지는 얼굴·털색·배경만 참조하고 포즈·구도는 따라하지 말 것", 깨끗한 프레임(나무·어두운 가장자리 물체·텍스트·워터마크 없음).
- 사용자가 올리면 망가진 점(정면 차렷, 어두운 그림자 등)을 확인하고 통과 시에만 다음으로. 이후 모든 이미지 프롬프트에 이 공통 블록과 "첨부: Ref-image"를 포함한다.

## 4단계: 씬별 반복
씬 n마다 아래 순서로, 각 항목 사이에 컨펌한다.
1. (첫 씬만) `C1-Start` 이미지 프롬프트 → 업로드 → 검수·컨펌.
2. `C{n}-End` 이미지 프롬프트 1개(첨부 이미지 이름 명시) → 업로드 → 검수(포즈, 시선, 소품 모양, 배경, 얼굴색 단계, 캐릭터 일관성)·컨펌.
3. `K{n}` 영상 프롬프트 1개 + Freepik 설정(스토리보드에서 정한 모델·방식, Start/End 방식이면 시작=C{n}-Start·끝=C{n}-End, Motion Control이면 시작 이미지 + 참조 영상 `ref/Motion-K{n}.mp4`, 정확한 초 단위 길이) → 사용자 업로드 → 검수.
4. 통과하면 `K{n}-Last`를 뽑아 보내고(끝 튀는 프레임 직전의 안정된 프레임, 마지막 1~3프레임은 제외) 씬 완료 컨펌을 받는다. 이것이 `C{n+1}-Start`가 된다.
5. 진행표를 보여 주고 다음 씬으로.

## 프롬프트 노하우 (오늘 배운 것)
### 이미지(GPT)
- 참조 이미지는 얼굴·털색·비례·배경만 참조한다고 맨 앞에 적는다. 안 그러면 참조 포즈를 베낀다.
- 포즈를 행동 세부로 적는다(어느 발이 어디, 시선, 자세). 부정문도 함께 써서 원치 않는 행동(손 내밀기 등)을 막는다.
- 이미지 편집은 "바꿀 것 딱 하나"만 쓰고 나머지는 바꾸지 말라고 하며, 포즈·머리 방향·소품 모양을 문장으로 고정한다. 편집이 자꾸 포즈를 바꾸면 올바른 원본을 첨부했는지 먼저 확인하고, 안 되면 새로 생성한다.
- 소품 잡기: 촬영 각도에서 잡는 발이 몸 뒤에 가려지면 소품이 공중에 뜬 것처럼 보인다. 소품은 항상 보이는 발이 줄기를 쥔 모양(배 높이)으로 설계하고, 잡는 장면이 잘 나온 이미지를 참조로 추가 첨부한다.
- 얼굴 홍조: 피부 부분(볼, 코 주변, 귀 안쪽, 이마 아래)만 칠하고 머리 털은 흰색 유지, 점·스티커 모양 금지로 써서 털 염색처럼 보이는 것을 막는다.

- 땜빵 편집 금지: 이미지가 불합격이면 직전 결과를 한 군데씩 고치는 편집을 반복하지 않는다(threads-viral-01 C1-Start v1~v5에서 하루 낭비). 지금까지 나온 모든 요구사항(상반신 분리·간격, 전원 프레임 안, 원본 첫 프레임 포즈·소품 각도, 캐릭터 외형)을 처음부터 한 프롬프트에 담고 **원본 프레임을 첨부해 새로 생성**한다. 프롬프트를 쓰기 전에 원본 프레임을 크롭해 포즈를 먼저 정확히 확인한다.
- 복잡한 포즈(원본의 특정 동작 재현)는 텍스트 묘사나 편집으로 맞추지 말고 사용자가 검증한 3단계 방식으로 만든다. 한 턴에 한 단계씩 준다.
  1) 원본 프레임(Pose-ref)을 첨부해 "이 이미지를 그대로 다시 그려라(워터마크만 제거)"
  2) 1단계 결과 + 캐릭터 Ref-image 첨부: "인물만 참조 인물로 교체, 포즈·위치·나머지는 그대로"
  3) 2단계 결과 + 직전 프레임(K{n-1}-Last) 첨부: "배경(장소·소품·카메라 구도)만 직전 프레임과 같게 교체, 인물 포즈는 그대로"
  여러 참조를 한 번에 섞는 프롬프트는 포즈가 무너진다(C6 실패 사례 v2·v3·v7).

### 영상(Freepik Wan)
- (이전 프로젝트 기준) Wan을 쓸 때는 한 프로젝트 안에서 고정한다. 클립마다 모델이 다르면 털·색·질감이 달라지고, 다른 모델은 지시를 무시하는 경우가 있었다. Wan 3.0은 길이를 초 단위로 정확히 지정할 수 있으니 매 클립마다 "길이: N초"로 정확한 숫자를 준다(구간 옵션으로 말하지 않는다). 계산: 목표 길이 × 속도 배수(Wan은 동작이 원본보다 느린 경향) + 끝 튀는 프레임 트림 여유 약 0.3초, 정수 초로 올림. 스토리보드 표에도 생성 초를 적는다. 해상도는 지정이 안 되므로 합본에서 720x1280·30fps로 맞춘다.
- 시간 순서대로 동작을 쓰고, 쓰지 않을 물건은 언급하지 않으며, 하단에 `Avoid:` 목록을 같은 블록에 넣는다.
- 배경 고정 문장을 항상 넣는다("wooden door, stone steps, flower pots stay visible, no trees"). 줌이 깊어지면 배경이 다른 장면으로 새는 경우가 많다.
- 두 발로 서기를 강조하고 Avoid에 `on four legs`, `walking on all fours`, `running like a dog`를 넣는다. "trots" 같은 단어는 네 발 달리기로 해석되므로 "shuffles in small hurried steps on his hind legs"로 쓴다.
- 소품이 사라지는 것을 막기 위해 "The rose stays clearly held by his visible paw in every frame"처럼 보이는 발과 지속을 명시하고, 모델이 가려지지 않는 방향으로 움직이게 한다. Avoid에 `rose disappearing`, `second rose`를 넣는다.
- 포즈를 유지해야 하는 캐릭터는 "stays in side profile"로 고정하고, 정면 응시는 Avoid에 넣는다.
- 머리·시선 회전처럼 약한 동작은 실패 확률이 높다. 두세 번 재생성을 안내하고, 안 되면 동작 반경을 줄이는 설계로 바꾼다. 503 같은 서버 오류는 크레딧 차감 없이 실패한 것이므로 다시 시도하라고 안내한다.
- 업로드된 영상 파일명에 모델명과 프롬프트 앞부분이 들어가므로 의도한 모델·프롬프트로 생성됐는지 확인한다.

- 인물이 경계선(문턱 등) 앞에서 멈추거나 물러서야 하는 장면: 시작 이미지가 걷는 중이면 Wan은 관성대로 계속 걸어 들어간다. "stops dead at the threshold, never takes another step forward, both feet stay behind the threshold the whole time"와 "recoils backward"를 시간 순서대로 쓰고, Avoid에 `stepping onto the poster`, `walking into the elevator`, `feet crossing the threshold`를 넣는다. 프롬프트에 "steps onto"처럼 전진 동사를 쓰지 않는다. 장면의 동기(예: 안 들어가려고 발버둥)를 프롬프트 첫 문장에 적는다.

- 프롬프트로 막아도 Wan이 경계선을 넘었다 돌아오면(K6 v1·v2: 문턱을 넘어 포스터에 섰다가 다시 나감) 프롬프트를 더 고치지 말고, 원본에서 그 사이 순간(예: 문턱 뒤에서 몸을 젖히는 10.13초)을 중간 키프레임 이미지로 만들어 클립을 둘로 나눈다(K{n}a: 시작→중간, K{n}b: 중간→끝). 중간 이미지도 3단계 방식으로 만든다.

- 영상 생성 전 시작·끝 이미지를 반드시 겹쳐 비교한다(같은 격자, 윤곽선 오버레이, 배경 ECC 정렬). 인물의 깊이(발 높이·몸 크기)와 카메라 배율이 다르면 Wan은 그 차이를 이동으로 채운다. 예: 시작은 걷는 중에 문턱을 밟고 있고 끝은 반걸음 뒤에 서 있으면, 관성대로 들어갔다가 뒤로 나오는 영상이 된다(K6 v1·v2·K6a-v1 실패). 해결: 끝 이미지와 같은 깊이에 있는 시작 프레임(K{n-1}의 더 이른 프레임)을 골라 K{n-1}-Last로 삼고, 배경은 ECC로 정렬한 보정본(-aligned)을 쓴다.

### Freepik 공식 튜토리얼 프롬프트 구조 (work/freepik-tutorial/analysis.md)
- 모델: Kling O1(Start/End image 지원), 해상도 1080, 길이 5"/10". Kling 2.6 Motion Control은 Start image + 참조 영상으로 동작을 그대로 복사(원본 영상의 동작 재현에 유력 — 다음 프로젝트에서 시험).
- 영상 프롬프트는 4부 구조로 쓴다:
  1) 한 줄 요약: 누가, 어디서, 무엇을 하고, 어떻게 끝나는가.
  2) 동작 문단: 인물 외형 + 동작을 시간 순서로, 태도 형용사(calm confidence 등). End image가 있으면 마지막 문장을 "… — matching the End Image composition."으로 끝낸다.
  3) 카메라 문단: 무브 이름(slow dolly-in, follows behind 등), 시작→끝 위치, 속도, 끝 프레임 구도. 고정 카메라면 "Static locked-off camera, no movement."
  4) 유지 문단: Same location, same lighting, same time of day, consistent realism. 핵심 배경 요소 나열. No new objects, no style changes.
- 튜토리얼은 Avoid 목록을 쓰지 않는다. 긴 Avoid 목록보다 유지 문단과 짧은 "No …"가 우선. 단, Wan처럼 금지가 필요했던 동작(문턱 넘기 등)은 동작 문단에 긍정형으로 쓴다("both feet stay behind the threshold").

- 원본 동작 재현(이 스킬의 핵심): **Motion Control**. 시작 이미지 = 원본 해당 구간 첫 프레임과 같은 구도·자세로 만든 우리 인물 이미지(3단계 방식), 참조 영상 = 원본 구간(내가 잘라 제공). 먼저 2.6 MC(저렴, 10초 이하)로 시험하고, 15초 구간이나 품질이 부족하면 3.0 MC.
- 시작/끝 이미지로 이어 붙이는 클립(동작 원본이 없는 장면)·여러 번 재시도할 장면: **Kling 2.5(무제한)**로 먼저 맞춰 보고, 품질이 필요하면 O1/2.6.
- 클립마다 모델을 바꾸면 질감·색이 달라지므로 한 프로젝트 안에서는 가능한 같은 계열을 유지하고, 바꾸면 합본 때 색 맞춤.

### 얼굴색(홍조) 처리 원칙
- 영상 모델은 클립 안에서 색을 서서히 바꾸지 못하고 끝 부근에서 점처럼 팍 생긴다. 한 클립 안에서는 시작·끝 이미지의 얼굴색 단계를 동일하게 하고 프롬프트에 "색 변화 없음"을 명시한다.
- 색 단계(흰색→연한 분홍→진한 분홍·빨강)가 바뀌는 곳은 다음 클립 시작 이미지를 편집해 만들고, 합본 때 얼굴 영역만 마스크로 느리게 디졸브하고 나머지는 빠르게 전환한다.

## 검수 체크리스트
- 이미지: 포즈, 시선, 장면 구도, 소품(잡는 발), 얼굴색 단계, 배경(나무 없음), 캐릭터 일관성.
- 영상: 프레임을 충분히 뽑아 ① 계획한 동작만 나왔는가 ② 두 발 서기 ③ 소품 유지 ④ 얼굴색이 중간에 튀지 않는가 ⑤ 배경 유지 ⑥ 끝 프레임 튐 ⑦ 카메라 줌 연속성.

## 5단계: 최종 동영상 생성(합본)
- 클립별 트림(끝 튀는 프레임 제거), 스토리보드의 속도 램프 적용, 720x1280·30fps 통일. 느리게 늘릴 구간은 광학 흐름 보간(OpenCV DIS)을 쓴다.
- 이음새: ECC 아핀 정렬 후 점진 적용, 짧은 디졸브(소품·머리 이중 상 방지가 필요하면 얼굴 타원 마스크로 느린/빠른 알파 분리). 밝기 보정은 컴파운딩 금지, 각 클립 끝에서 1.0으로 복귀하게 감쇠시킨다.
- libx264 crf16 yuv420p로 쓰고 마지막 장면을 약 1초 홀드한다.
- 이음새 프레임 스트립을 눈으로 확인하고(잔상·튀는 프레임·밝기 차이) 프레임 차이를 수치로 확인한다.
- `Final-v{n}.mp4`를 SendUserFile로 전달하고 느낀 점을 시간대로 묻는다. 수정 요청은 해당 씬의 속도·트림·이음새만 고치고 재합본한다. 클립 목록(파일, 마지막 프레임, 속도 시작·끝, 이음새 겹침 프레임 수)은 `scripts/build.py`에 모아 두고 버전을 남긴다.

### 합본 노하우 (엘리베이터 프로젝트에서 배운 것)
- 배속은 클립 전체에 하나만 걸지 말고 동작 구간별로 나눠 건다(예: 손 올리기 1.7배, 뒷걸음 2.0배). 원본과 나란히 놓고 프레임당 움직임 수치를 비교한다.
- 배속으로 느낌(화남, 발악)이 안 나오면 배속을 더 올리지 말고 동작 자체를 다시 생성한다("빠르게 팔을 아래로 뿌리친다"처럼 세기를 쓴다). 동작이 부족하면 중간 키프레임을 추가해 클립을 나눠 프레임 수를 늘린다.
- 끝 튐은 마지막 몇 프레임만 보지 말고, 몸이 끝 이미지 쪽으로 되돌아가는 구간 전체를 찾아 그 직전에서 자른다. 사용자가 정지 화면을 주면 그 프레임과 매칭해 정확히 자른다.
- 새로 그린 시작 이미지(GPT로 배경까지 다시 그린 것)는 직전 클립과 배경 선이 부분적으로 다 어긋난다. 디졸브·모핑·전체 이동 보정으로는 티가 난다. 해결 순서: ① 연결 클립(직전 Last → 새 시작 이미지)을 생성해 걷던 동작을 멈춤 자세로 만든다 ② 이후 클립 그룹 전체를 직전 클립 마지막 프레임에 조밀 광학흐름(σ≈8 평활)으로 비강체 정렬하고 LAB 색 맞춤 ③ 멈춘 자세끼리 짧은 디졸브. 예방: 시작 이미지는 새로 그리지 말고 직전 K-Last를 편집해 인물만 바꾼다.

## 5-1단계: 오디오(사용자가 요청할 때)
- Freepik 음악(Music)과 효과음(Sound Effects, 내부적으로 ElevenLabs)을 쓴다. **효과음 최소 길이는 3초**이므로 길이는 3초 이상으로 지시하고, 필요한 부분만 편집에서 잘라 쓴다. 음악은 영상보다 길게(20~30초) 받는다.
- 사용자가 편집한 최종 영상이 오면 그 영상으로 타임라인을 다시 분석한 뒤 오디오를 설계한다.
- 구성: 배경음악 1개 + 핵심 순간 효과음(문 띵, 놀람 스팅, 인서트 앰비언스, 화난 동작 휙). 음악은 클라이맥스 순간에 뚝 끊고 인서트 동안 무음, 이후 더 신나는 뒷부분으로 재개.
- 받은 파일은 0.05초 단위 RMS로 구간(타격음 위치, 무음, 꼬리)을 측정해 핵심 타격 지점을 영상 동작 프레임에 정확히 맞추고, 중간 무음은 잘라낸다. 아이템마다 합친 미리보기를 보낸다.

## 6단계: 쓰레드 포스팅 샘플 글

- 구성: 첫 줄 훅(스크롤을 멈추는 한 문장), 영상 속 상황에 공감할 포인트 1~2줄, 마무리 한 줄. 이모지는 절삭해서 쓰고 해시태그는 소수만.
- 댓글 달라고 직접 요청하지 않아도 자연스럽게 공감해서 댓글을 달 수밖에 없는 문구(내 경험을 떠올리게 하는 고백형·질문형 등)를 고른다. 안을 2~3개 만들어 하나씩 장단점과 함께 보여 주고 권장안을 표시한다. 한국어이며, 유머와 공감 톤을 사용자와 다듬는다.
- 음악·자막은 사용자가 원할 때만 만든다.
