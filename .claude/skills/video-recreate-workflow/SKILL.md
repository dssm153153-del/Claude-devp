# video-recreate-workflow

사용자가 참고 영상(바이럴 숏폼 등)을 주고 "이것과 같은 영상을 다른 캐릭터/장소로 만들자"고 할 때 사용한다. 대화는 한국어, 파일명은 영어.

역할 분담: 사용자는 GPT로 이미지를, Freepik(Wan, 시작·끝 이미지 방식)으로 영상을 직접 생성해 업로드한다. Claude는 분석, 설계, 프롬프트 작성, 결과 검수(ffmpeg/OpenCV), 프레임 추출, 최종 합본, 쓰레드 글 작성을 맡는다.

## 전체 순서 (건너뛰지 않는다)
1. 영상 분석
2. 씬 상세 설계 (스토리보드)
3. 샘플 이미지 (Ref-image)
4. 씬별 반복: GPT 이미지 생성 → Freepik 영상 생성 → 검수 → 컨펌 → 다음 씬
5. 최종 동영상 생성(합본)
6. 쓰레드 포스팅 샘플 글 작성

각 단계가 끝나면 사용자에게 컨펌을 받고 다음으로 넘어간다. 컨펌 없이 앞서가지 않는다.

## 핵심 규칙
1. 한 번에 하나씩. 한 턴에 아이템 1개(이미지 프롬프트 1개 또는 영상 프롬프트 1개)만 준다. 여러 개를 한꺼번에 주지 않는다.
1-1. 매 턴에는 지금 아이템에 필요한 정보만 준다(생성 초, 첨부, 설정, 프롬프트). 다음·전체 아이템 표나 미래 정보를 미리 주지 않는다. 설정이 바뀌면 그 아이템의 설정+프롬프트 전체를 다시 줘서 사용자가 위로 스크롤할 필요가 없게 한다.
2. 프롬프트는 항상 완전한 코드블록 1개. 공통 블록을 포함해 복사·붙여넣기만 하면 되게 한다. "이 문장을 추가하세요" 같은 조각 지시는 금지. 영상 프롬프트는 동작 설명 + 배경 고정 + `Avoid:` 목록을 한 블록에 넣는다.
3. 결과물을 받으면 직접 분석한다(프레임 추출, 컨택트시트, 프레임 차이). "좋아 보여요"가 아니라 통과/불합격과 근거(동작, 색, 연속성, 끝 튀는 프레임)를 말한다.
4. 실패하면 프레임으로 원인을 진단한 뒤 고친다. 프롬프트만 길게 늘리지 말고, 모델이 구조적으로 못 하는 동작인지도 판단한다.
5. 용어와 파일명을 혼용하지 않는다.
6. 요청 없이 커밋·푸시하지 않는다. 확정된 자산을 레포에 저장·커밋할지는 시작 때 한 번만 묻는다.
7. 매 턴 현재 위치를 "지금: C3-End 이미지 → 다음: K3 영상"처럼 이름으로 표시하고, 씬이 끝날 때마다 진행표(아이템 / 상태: 확정·진행·대기)를 보여준다.

## 매 턴 보내기 전 자가 점검 (어기면 사용자 한도 낭비)
보내기 전에 아래를 모두 확인하고, 하나라도 빠지면 고친 뒤 보낸다.
- [ ] 이미지 프롬프트: 첨부에 캐릭터 기준 Ref-image(해당 인물의 Ref-image-A/B)가 항상 들어 있는가. 직전 프레임(K{n-1}-Last)만 첨부하지 않는다. 형식: "생성 파일명: X / 첨부: 직전 프레임, Ref-image-?"(포스터·소품 기준 이미지가 따로 있으면 그것도).
- [ ] 첨부마다 무엇을 참조하고 무엇을 베끼지 말지(포즈·위치·소품) 프롬프트 첫 줄에 적었는가.
- [ ] 영상 프롬프트: 모델명, 시작·끝 이미지 파일명, 정확한 생성 초(N초)를 적었는가.
- [ ] 지금 아이템 하나만 주는가. 미래 아이템 표나 불필요한 설명을 빼고 짧게 쓴다.
- [ ] 검수는 프레임을 실제로 보고 수치(픽셀 차이·움직임)로 근거를 댔는가. 배속이 필요하면 원본과 나란히 비교한 미리보기를 보낸다.
- [ ] 앞 턴에서 사용자가 지적한 실수를 반복하지 않는가.

## 네이밍 규칙
- C = 이미지, K = 영상.
- `Ref-image.png`: 전체 기준 샘플 이미지(캐릭터·털색·표정·배경·조명). 여러 장이면 `Ref-image-A.png`, `Ref-image-B.png`.
- `C{n}-Start.png`: 씬 n의 시작 이미지. 첫 씬만 새로 생성하고, 이후는 직전 `K{n-1}-Last.png`를 그대로 쓰거나 필요한 부분만 편집한다.
- `C{n}-End.png`: 씬 n의 끝 이미지(새로 설계해 생성).
- `K{n}.mp4`: 씬 n의 영상. 재생성본은 `K{n}-v2.mp4`.
- `K{n}-Last.png`: K{n}에서 내가 뽑은 마지막 유효 프레임(끝 이미지로 튀는 프레임 직전).
- `Final-v{n}.mp4`: 합본 버전.
- `Threads-post.md`: 쓰레드 샘플 글.
- 폴더: `work/{project}/` 아래에 `analysis/`, `ref/`, `images/`, `clips/`, `frames/`, `final/`, `scripts/`, `copy/`.
- 사용자가 다른 이름으로 업로드해도 내가 위 이름으로 저장하고 알려 준다. 이미지를 보낼 때는 파일명을 캡션에 붙이고, 첨부해야 할 이미지를 이름으로 지시한다("첨부: Ref-image, K5-Last").

## 1단계: 영상 분석
분석이 틀리면 이후 모든 이미지·영상이 이상한 동작이 되어 "웃긴 영상"이 아니라 "비웃는 영상"이 된다. 작은 썸네일과 움직임 수치로 이야기를 짜 맞추지 않는다. 실제 실패 사례: 1fps/4fps 작은 컨택트시트만 보고 "문 밖에서 지인에게 작별 인사하다 늦게 엘리베이터를 타려는 사람"을 "엘리베이터 안에서 두리번거리는 사람"으로 오독했다.

1. 자동 측정: `python3 -I scripts/analyze.py <video> work/{project}/analysis/auto` (스킬 폴더의 `scripts/analyze.py`; 없으면 동일 로직으로 작성). opencv-python-headless가 없으면 먼저 설치한다. 결과:
   - `info.txt`: 해상도·fps·길이·오디오
   - `sheets/tXXX.png`: 2초마다 1장, 0.2초(5fps) 간격, 288px 폭, 프레임마다 타임코드 표시
   - `report.txt`: 컷 위치(프레임 차이 급증), 샷 목록, 0.5초 단위 움직임·줌 곡선, 반복 구간(티저·리플레이 자동 검출)
2. 시트를 처음부터 끝까지 한 장도 빼지 않고 직접 본다. 1fps 요약 시트만으로 결론 내지 않는다. 동작이 빠르거나 핵심인 구간은 10fps·더 큰 폭으로 다시 뽑아 본다.
3. 먼저 공간 구조를 확정한다: 카메라 위치(어디에 붙어 어느 쪽을 보는지), 화면의 위·아래·좌·우가 실제로 무엇인지(바닥/로비/문/손잡이), 인물이 어느 공간에 서 있는지, 화면 밖 인물·장소(지인, 입구 방향). 이걸 틀리면 동작 해석이 전부 틀린다.
4. 0.2초 단위 상세 타임라인 표를 쓴다: 시간 / 인물 / 시선 방향 / 팔·다리·몸 동작 / 소품 상태 / 문·배경 상태. "두리번거림"처럼 뭉뚱그린 단어 대신 "오른팔을 높이 들고 화면 왼쪽을 보며 손을 흔들고 게걸음"처럼 관찰한 그대로 쓴다.
5. 동기(왜 그 동작을 하는가)를 적는다: 예) 인사하느라 문 열린 걸 늦게 봄 → 바닥을 낭떠러지로 착각 → 타지 않으려고 손잡이에 매달려 다리를 차올림. 웃음 포인트는 동기와 반전에서 나온다.
6. 컷 표(번호, 시간, 내용, 티저·인서트 여부)와 페이스(정적·폭발 구간, 움직임 수치 근거)를 정리한다. 티저가 본편 어느 구간의 복사인지 수치로 밝힌다.
7. 웃음 포인트 목록을 만든다.
8. 결과를 `analysis/analysis.md`에 저장하고, 핵심 구간 시트를 SendUserFile로 같이 보여 주며 컨펌을 받는다. 사용자가 해석을 정정하면 그 구간을 다시 고해상도로 뽑아 확인한 뒤 고친다(사용자 말만 받아 적지 않는다).

## 2단계: 씬 상세 설계
분석 결과로 스토리보드 표를 만든다: 씬 번호, 상황, 카메라(시작/끝), 캐릭터별 동작과 포즈, 소품 상태, 표정·얼굴색 단계, 목표 길이, 속도 배수(합본 때 적용), 이음새 처리 메모.
- 길이와 속도는 일부러 다양하게 설계한다(모두 5초·동일 속도 금지). 원본의 정적→빠른 접근→느린 클로즈업→빠른 퇴장 같은 리듬을 따른다.
- 얼굴색 변화처럼 모델이 클립 안에서 못 하는 것은 이 단계에서 이음새 편집으로 처리하기로 미리 정한다(아래 노하우 참고).
- 씬 목록 전체를 컨펌받고 시작한다. 이후 변경은 사용자와 합의 후 표를 갱신한다.

## 3단계: Ref-image
- 모든 것의 기준이 되는 샘플 이미지를 이미지 생성 전에 가장 먼저 만든다. 이 방식으로 품질이 확실히 좋아진다.
- Ref-image 프롬프트는 공통 블록을 담은 완전한 코드블록 1개.
- 공통 블록: 포토리얼리스틱 시네마틱, 9:16, 측면 눈높이, 85mm, 얕은 피사계심도, 골든아워 조명, 캐릭터 A/B 외형 묘사(털색·길이·표정), 두 발로 서기, 배경 설명, 소품 1개, "참조 이미지는 얼굴·털색·배경만 참조하고 포즈·구도는 따라하지 말 것", 깨끗한 프레임(나무·어두운 가장자리 물체·텍스트·워터마크 없음).
- 사용자가 올리면 망가진 점(정면 차렷, 어두운 그림자 등)을 확인하고 통과 시에만 다음으로. 이후 모든 이미지 프롬프트에 이 공통 블록과 "첨부: Ref-image"를 포함한다.

## 4단계: 씬별 반복
씬 n마다 아래 순서로, 각 항목 사이에 컨펌한다.
1. (첫 씬만) `C1-Start` 이미지 프롬프트 → 업로드 → 검수·컨펌.
2. `C{n}-End` 이미지 프롬프트 1개(첨부 이미지 이름 명시) → 업로드 → 검수(포즈, 시선, 소품 모양, 배경, 얼굴색 단계, 캐릭터 일관성)·컨펌.
3. `K{n}` 영상 프롬프트 1개 + Freepik 설정(시작=C{n}-Start, 끝=C{n}-End, 모델 Wan 고정, 정확한 초 단위 길이) → 사용자 업로드 → 검수.
4. 통과하면 `K{n}-Last`를 뽑아 보내고(끝 튀는 프레임 직전의 안정된 프레임, 마지막 1~3프레임은 제외) 씬 완료 컨펌을 받는다. 이것이 `C{n+1}-Start`가 된다.
5. 진행표를 보여 주고 다음 씬으로.

## 프롬프트 노하우 (오늘 배운 것)
### 이미지(GPT)
- 참조 이미지는 얼굴·털색·비례·배경만 참조한다고 맨 앞에 적는다. 안 그러면 참조 포즈를 베낀다.
- 포즈를 행동 세부로 적는다(어느 발이 어디, 시선, 자세). 부정문도 함께 써서 원치 않는 행동(손 내밀기 등)을 막는다.
- 이미지 편집은 "바꿀 것 딱 하나"만 쓰고 나머지는 바꾸지 말라고 하며, 포즈·머리 방향·소품 모양을 문장으로 고정한다. 편집이 자꾸 포즈를 바꾸면 올바른 원본을 첨부했는지 먼저 확인하고, 안 되면 새로 생성한다.
- 소품 잡기: 촬영 각도에서 잡는 발이 몸 뒤에 가려지면 소품이 공중에 뜬 것처럼 보인다. 소품은 항상 보이는 발이 줄기를 쥔 모양(배 높이)으로 설계하고, 잡는 장면이 잘 나온 이미지를 참조로 추가 첨부한다.
- 얼굴 홍조: 피부 부분(볼, 코 주변, 귀 안쪽, 이마 아래)만 칠하고 머리 털은 흰색 유지, 점·스티커 모양 금지로 써서 털 염색처럼 보이는 것을 막는다.

### 영상(Freepik Wan)
- 모델은 Wan으로 고정한다. 클립마다 모델이 다르면 털·색·질감이 달라지고, 다른 모델은 지시를 무시하는 경우가 있었다. Wan 3.0은 길이를 초 단위로 정확히 지정할 수 있으니 매 클립마다 "길이: N초"로 정확한 숫자를 준다(구간 옵션으로 말하지 않는다). 계산: 목표 길이 × 속도 배수(Wan은 동작이 원본보다 느린 경향) + 끝 튀는 프레임 트림 여유 약 0.3초, 정수 초로 올림. 스토리보드 표에도 생성 초를 적는다. 해상도는 지정이 안 되므로 합본에서 720x1280·30fps로 맞춘다.
- 시간 순서대로 동작을 쓰고, 쓰지 않을 물건은 언급하지 않으며, 하단에 `Avoid:` 목록을 같은 블록에 넣는다.
- 배경 고정 문장을 항상 넣는다("wooden door, stone steps, flower pots stay visible, no trees"). 줌이 깊어지면 배경이 다른 장면으로 새는 경우가 많다.
- 두 발로 서기를 강조하고 Avoid에 `on four legs`, `walking on all fours`, `running like a dog`를 넣는다. "trots" 같은 단어는 네 발 달리기로 해석되므로 "shuffles in small hurried steps on his hind legs"로 쓴다.
- 소품이 사라지는 것을 막기 위해 "The rose stays clearly held by his visible paw in every frame"처럼 보이는 발과 지속을 명시하고, 모델이 가려지지 않는 방향으로 움직이게 한다. Avoid에 `rose disappearing`, `second rose`를 넣는다.
- 포즈를 유지해야 하는 캐릭터는 "stays in side profile"로 고정하고, 정면 응시는 Avoid에 넣는다.
- 머리·시선 회전처럼 약한 동작은 실패 확률이 높다. 두세 번 재생성을 안내하고, 안 되면 동작 반경을 줄이는 설계로 바꾼다. 503 같은 서버 오류는 크레딧 차감 없이 실패한 것이므로 다시 시도하라고 안내한다.
- 업로드된 영상 파일명에 모델명과 프롬프트 앞부분이 들어가므로 의도한 모델·프롬프트로 생성됐는지 확인한다.

### 얼굴색(홍조) 처리 원칙
- 영상 모델은 클립 안에서 색을 서서히 바꾸지 못하고 끝 부근에서 점처럼 팍 생긴다. 한 클립 안에서는 시작·끝 이미지의 얼굴색 단계를 동일하게 하고 프롬프트에 "색 변화 없음"을 명시한다.
- 색 단계(흰색→연한 분홍→진한 분홍·빨강)가 바뀌는 곳은 다음 클립 시작 이미지를 편집해 만들고, 합본 때 얼굴 영역만 마스크로 느리게 디졸브하고 나머지는 빠르게 전환한다.

## 검수 체크리스트
- 이미지: 포즈, 시선, 장면 구도, 소품(잡는 발), 얼굴색 단계, 배경(나무 없음), 캐릭터 일관성.
- 영상: 프레임을 충분히 뽑아 ① 계획한 동작만 나왔는가 ② 두 발 서기 ③ 소품 유지 ④ 얼굴색이 중간에 튀지 않는가 ⑤ 배경 유지 ⑥ 끝 프레임 튐 ⑦ 카메라 줌 연속성.

## 5단계: 최종 동영상 생성(합본)
- 클립별 트림(끝 튀는 프레임 제거), 스토리보드의 속도 램프 적용, 720x1280·30fps 통일. 느리게 늘릴 구간은 광학 흐름 보간(OpenCV DIS)을 쓴다.
- 이음새: ECC 아핀 정렬 후 점진 적용, 짧은 디졸브(소품·머리 이중 상 방지가 필요하면 얼굴 타원 마스크로 느린/빠른 알파 분리). 밝기 보정은 컴파운딩 금지, 각 클립 끝에서 1.0으로 복귀하게 감쇠시킨다.
- libx264 crf16 yuv420p로 쓰고 마지막 장면을 약 1초 홀드한다.
- 이음새 프레임 스트립을 눈으로 확인하고(잔상·튀는 프레임·밝기 차이) 프레임 차이를 수치로 확인한다.
- `Final-v{n}.mp4`를 SendUserFile로 전달하고 느낀 점을 시간대로 묻는다. 수정 요청은 해당 씬의 속도·트림·이음새만 고치고 재합본한다. 클립 목록(파일, 마지막 프레임, 속도 시작·끝, 이음새 겹침 프레임 수)은 `scripts/build.py`에 모아 두고 버전을 남긴다.

## 6단계: 쓰레드 포스팅 샘플 글
- 영상 컨펌 후 작성한다. 결과는 `copy/Threads-post.md`로 저장하고 대화에도 복사해 쓸 수 있게 보여 준다.
- 구성: 첫 줄 훅(스크롤을 멈추는 한 문장), 영상 속 상황에 공감할 포인트 1~2줄, 마무리 한 줄. 이모지는 절삭해서 쓰고 해시태그는 소수만.
- 댓글 달라고 직접 요청하지 않아도 자연스럽게 공감해서 댓글을 달 수밖에 없는 문구(내 경험을 떠올리게 하는 고백형·질문형 등)를 고른다. 안을 2~3개 만들어 하나씩 장단점과 함께 보여 주고 권장안을 표시한다. 한국어이며, 유머와 공감 톤을 사용자와 다듬는다.
- 음악·자막은 사용자가 원할 때만 만든다.
